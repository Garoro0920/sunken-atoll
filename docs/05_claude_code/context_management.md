# コンテキスト管理

## 1. 目的

LLM の有限な **コンテキストウィンドウ** を効率良く使い、長期セッション・大規模プロジェクトでも品質を維持する。

## 2. 基本原則

1. **必要十分**: 関係しないファイルを読まない、貼らない
2. **要約優先**: 巨大成果物は要約して取り込む
3. **構造化**: 表・JSON・箇条書きの方が散文より圧縮効率が高い
4. **永続化と分離**: 文脈を会話に積むより、ファイルに残し参照する
5. **再構成可能**: 文脈を失っても `docs/` と `pipeline/decisions/` から復元できる構造

## 3. 入力選別

セッション開始時に Claude Code が必要十分な範囲だけ読む:
- 直接関与する `src/`、`scenes/` ファイル
- 該当する spec / docs / decisions
- 触らないファイルは要約か索引で済ます

不要範囲を読み込むと:
- 文脈消費が早まる
- 関係ない箇所まで「修正」しがち
- リトライで往復が増える

## 4. 出力圧縮

- 進捗通知は 1 文
- 完了報告は 1〜2 文
- 詳細はファイル参照で済ます(`path:line`)
- 表形式は過剰列を持たない

## 5. 巨大ファイル / 大量ファイル

- 全文ではなく **要約** か **必要部分** を読み込む
- ヒット箇所を Grep で限定してから Read
- 検索のための予備コールを許容(コスト < 後の混乱)

## 6. ログ・スクリーンショット・テスト出力

- 全文を会話に貼らない
- 失敗箇所のみを抽出 / 該当行 ±5 行
- スクリーンショットは Vision に直接渡し、結果(構造化 JSON)のみ会話に

## 7. 永続化先の使い分け

| 内容 | 保管先 |
|---|---|
| 規約・恒久ルール | `docs/` |
| プロジェクト固有の不可逆経緯 | `CLAUDE.md` or Claude Code メモリ |
| 設計判断・調査結果 | `pipeline/decisions/<date>.md` |
| 仕様 | `specs/` |
| タスク状態 | TaskCreate/TaskList |
| 一時メモ | セッション内会話のみ(残さない) |

## 8. 圧縮の合図

次のような場合は **要約 → 新セッション** を検討:
- 同じファイルを何度も再読込している
- 提案の一貫性が崩れ始めた
- 過去発言の参照ミスが出始めた
- 出力が冗長化してきた

## 9. キャッシュ

- LLM プロンプトキャッシュ(該当モデルが対応する場合)を活用
- 大きなシステムプロンプトを安定化させ、変更頻度を下げる
- Anthropic SDK 等での `cache_control` を採用検討

## 10. ハイブリッド戦略

- 構造化情報(設定、データ)は **テキストファイルに永続化**
- 流動情報(進行中の文脈)は **会話に保持**
- 両者の境界を明確にする

## 11. メタ会話の最小化

- 「考えている」「確認します」のような前置きを避ける
- 用件に直接入る
- 質問は 1 つに集約する

## 12. ストリーミング系の扱い

- NPC ランタイム LLM や Vision ストリームは別プロセスで処理
- 会話の文脈には結論のみを反映

## 13. アンチパターン

- 「念のため全部読む」
- 「念のため全部要約する」
- 巨大 JSON / ログのフル貼付
- 過去会話の長文引用
- 重複した同義の指示
