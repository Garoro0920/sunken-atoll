# プロンプト設計ガイド

## 1. 目的

`prompt_templates.md` がコピー利用前提の「型」を提供するのに対し、本ドキュメントは **プロンプトを設計するときの原則・思考順序** を扱う。新規ユースケース、既存テンプレートでは収まらない要求、品質劣化が見られた既存プロンプトの再設計などに使う。

## 2. 設計の前提

- LLM は「指示 + 文脈 + 制約」を 1 度の入出力で処理する関数だと考える
- プロンプトは **コードの一部** であり、Git 管理・変更履歴・テスト対象とする
- 良いプロンプトは **再現性**(同じ入力で同じ品質)と **改変容易性**(部分修正で挙動制御)を持つ

## 3. 設計の順序

1. **目的を 1 文で書く**(何を作る/判定する/変換するか)
2. **入力スキーマと出力スキーマ** を確定する(構造化を最優先)
3. **正例 / 反例** を最低 1 組ずつ用意する
4. **制約** を列挙する(長さ、禁止語、ライセンス、安全性)
5. **失敗時の挙動** を定義する(エラー JSON、空配列など)
6. **温度 / シード / 最大トークン** を仮置きする
7. **小さな実例で動かす** → 評価 → 修正 をループ

## 4. プロンプトの基本構造

```
[role/context]    あなたは <役割>。前提として <重要文脈>。
[task]            次のタスクを実行: <一文>
[input]           <構造化入力 or テキスト>
[constraints]     - 守るべき条件
                  - 禁止事項
                  - 出力長さ
[examples]        正例 / 反例(任意、ただし強力)
[output_schema]   厳密な形式定義(JSON Schema 推奨)
[failure_mode]    指示不能時の応答(例: {"error": "..."} を返す)
```

## 5. 構造化出力

- 自由記述より **JSON / YAML / 厳密フォーマット** を強く優先
- 受信側で機械パースし、失敗したら自動再試行
- スキーマは別途バージョン管理する

例(視覚回帰判定):
```json
{
  "issues": [
    { "type": "missing_texture", "region": "center", "confidence": 0.9 }
  ],
  "overall_pass": false,
  "notes": "..."
}
```

## 6. 制御パラメータ

| パラメータ | 役割 | 既定の考え方 |
|---|---|---|
| temperature | 多様性 vs 安定性 | 検証/分類は低、創造は中、ブレストは高 |
| top_p | サンプリング窓 | 多くの場合 temperature と二者択一 |
| seed | 再現性 | 本番は固定、A/B 比較は変動 |
| max_tokens | 上限 | 想定 + マージン、無闇に大きくしない |
| stop sequences | 終端制御 | 構造化出力で末尾汚染を防ぐ |

## 7. システムプロンプトの作法

- **役割と制約は冒頭** に置く(モデルが最重要視する位置)
- 否定語(〜しない)は **肯定語の言い換え** に置換できないか検討
- 長文化したら **箇条書き化** + 重要事項を再強調
- 「重要」「必ず」を多用しすぎると重み付けが薄れる

## 8. ユーザプロンプトの作法

- **何を欲しているか / なぜ必要か / どう使うか** の 3 点を必要十分に
- 巨大文脈は要約して渡す(全文を貼らない)
- 既存テンプレートに寄せられるなら寄せる(本ガイドより `prompt_templates.md` を優先)

## 9. 生成系 API 向け作法

- **属性の列挙が強い**(例: 3D メッシュ「dragon, dark fantasy, scarred, perched, low poly, game-ready」)
- **negative プロンプト** で除外を明示
- **スタイル参照画像 / シード** を使い再現性を確保
- 専門語(レンダリング・撮影・物理)は学習データに沿った用語を選ぶ

## 10. 反パターン

- 賛辞語の多用(masterpiece, best quality 等は薄い)
- 多義語(simple, beautiful)の単独使用
- 矛盾する指示の同時記述
- 出力スキーマを言葉で曖昧に説明する(JSON Schema を貼る)
- セッション毎に微妙に異なる版を使う(版管理せよ)

## 11. プロンプト評価

評価軸を決めてから走らせる:
- **正確性**: 期待出力に対する一致 / 機械パース成功率
- **多様性**: 重複生成率
- **安全性**: 禁止語含有率、ハルシネーション率
- **コスト**: 平均トークン、平均レイテンシ
- **品質**: 人間 / Vision による主観評価

評価結果は `pipeline/prompts/evaluations/` に蓄積。

## 12. A/B 比較

- 1 変数のみ変更し、N サンプル比較
- 同一シード・同一入力で公平比較
- 統計的有意性を意識(N が小さければ参考値)

## 13. プロンプトのリファクタ

- 重複ブロックを共通定数化(テンプレート変数)
- 長文プロンプトは「役割」「制約」「ガイダンス」「例」「出力形式」のブロックに分割
- 改訂は PR + 旧版との差分

## 14. 安全プロンプト

- 倫理ガードは `07_governance/ai_ethics.md` を参照し、システムプロンプトに反映
- ジェイルブレイク試行への応答方針を共通化
- ユーザ入力の引用には **二重引用 + サニタイズ**

## 15. NPC ランタイム LLM 特有の注意

- **コンテキストが累積する** ため、要約圧縮戦略を持つ
- 「忘れないでほしい事実」と「忘れていい雑談」を分離
- 役柄が崩れたときの復帰プロンプトを用意

## 16. 更新と廃止

- 旧プロンプトは即時削除しない(再現用途で残す)
- 廃止時は理由を `pipeline/prompts/templates/CHANGELOG.md` に明記
