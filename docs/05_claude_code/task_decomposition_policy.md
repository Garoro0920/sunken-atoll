# タスク分解ポリシー

## 1. 目的

`task_management.md` がタスクの **追跡** を扱うのに対し、本ドキュメントは要求や仕様を **どう刻んでタスクにするか** の指針を定める。

## 2. 良い分解の条件

- 1 タスク = 1 完了条件(二値判定可能)
- 1 タスク = 30 分〜2 時間で完了できる規模が目安
- タスク間の依存が **テキスト 1 行で説明可能**
- 並列可能な兄弟タスクが存在する(直列化を最小化)

## 3. 分解の手順

```
[1] 仕様/要求を 1 文で言い換える
[2] 受入基準(DoD)を箇条書きで列挙
[3] DoD を満たすために必要な「成果物」を列挙
[4] 成果物ごとに「作る/変える/消す」を動詞化 → タスク候補
[5] 依存関係を矢印で書き、並列可能なものを束ねる
[6] 各タスクに完了条件と検証手段を付ける
[7] 不確実性が高いタスクは「調査/プロトタイプ」を別タスクに
```

## 4. 分解の単位

| カテゴリ | 例 |
|---|---|
| 設計 | 「ボス AI の状態機械を設計する」 |
| アセット | 「ボスメッシュを生成する」 |
| 実装 | 「ボスの攻撃 1 を実装する」 |
| シーン | 「ボスアリーナのシーンを構築する」 |
| テスト | 「ボス戦シナリオテストを追加する」 |
| ドキュメント | 「攻撃パターンを spec に追記する」 |

## 5. 分解の深さ

- 大: エピック(週単位)
- 中: 機能(数日)
- 小: タスク(数時間)
- 極小: ステップ(数分)

Claude Code は **小〜中** を扱う。エピックは spec で表現し、Claude Code は分解段階から関与してよい。

## 6. 並列化の指針

- 触るファイル群が **重ならない** タスクは並列可
- 触るファイルが重なるが論理的に独立な変更も並列可(ただしマージ戦略要)
- 共通基盤に依存する派生タスクは基盤タスク完了後に並列展開

## 7. 分解アンチパターン

- 「リファクタ」を 1 タスクに丸める(成果物が見えない)
- 「とりあえず実装」を完了条件にする(検証不能)
- 1 タスクに無関係な複数機能を詰める
- 分解しすぎて 100 件以上になる(管理コスト過剰)
- 既存タスクと重複するタスクを増やす

## 8. 分解の早期検知

次に該当する兆候はタスクを **再分解** すべき:
- 1 タスクで 3 つ以上の DoD を抱える
- ステータスが in_progress のまま 1 日進まない
- レビューで「変更が大きすぎて見られない」と指摘される
- テストの追加が「全機能カバー」と曖昧化する

## 9. ブロッカーの扱い

- 外部要因なら理由・解除条件・期限をタスクに記録
- 自力で解消可能な技術ブロッカーは **ブロッカー解消用タスク** を派生させ in_progress を維持

## 10. 不確実性タスク

- 「調査」「プロトタイプ」「試し書き」と明示
- 完了条件は「結論」または「実装方針の決定」
- 結果を `pipeline/decisions/` に短く残す

## 11. 仕様変更時

- 影響タスクを洗い直す
- 部分破棄(deleted)・新規作成・更新を切り分ける
- 分解の根拠を spec の改訂履歴に残す

## 12. Claude Code への引渡し

- 各タスクには「触ってよいパス」「触らないパス」を明示
- 期待される検証手段(テスト・コマンド)を明示
- 関連 spec / docs へのリンクを必ず添付

## 13. 例

仕様: 「ボス戦を追加する(ボス、3 種攻撃、専用 BGM、シナリオで遭遇/勝利/敗北)」

分解(中):
1. 仕様詳細化(spec.md 完成)
2. ボスメッシュ生成 + リグ
3. ボス攻撃モーション 3 種生成
4. ボス AI 状態機械実装
5. ボス用シェーダ調整
6. ボス戦 BGM 生成
7. ボスアリーナシーン構築
8. シナリオ統合(遭遇トリガ、勝敗判定)
9. シナリオテスト追加
10. 視覚回帰ベースライン追加
11. ドキュメント更新

このうち 2,3,6 は並列、4,5 は仕様詳細化後に並列、7 は 2,3,4,5 完了後、8 は 7 完了後、9,10,11 は 8 完了後。
