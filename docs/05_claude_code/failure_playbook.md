# 失敗対応プレイブック

## 1. 目的

Claude Code が遭遇しがちな **典型失敗** に対する、即応可能な手順集。`incident_response_workflow.md` がプロジェクト全体の障害対応であるのに対し、本ドキュメントは Claude Code の作業中に起きる**個別の失敗** を対象とする。

## 2. 共通フロー

```
[1] 観察: 何が、いつ、どこで起きたか(エラーメッセージ、ファイル、行)
[2] 切り分け: 自分の変更起因か、外部起因か、環境起因か
[3] 仮説: 上位 3 つを列挙
[4] 検証: 安価な検証から実行
[5] 修正: 最小範囲で修正
[6] 再発防止: テスト / 規約 / ドキュメント更新
```

## 3. 典型失敗カタログ

### 3.1 GDScript / C# のコンパイル失敗
- メッセージから対象ファイル・行・型情報を抽出
- 型ヒント不一致は最も多い → シグネチャを逆算
- `class_name` 衝突は別名 or リネーム
- 軽微なら自動修正、規約絡みなら規約優先

### 3.2 Godot インポート警告 / 失敗
- まず `--import` 単体で再現
- 共通原因: `.import` の参照切れ、テクスチャ/メッシュの不正、シェーダエラー
- 警告 0 を維持(品質ゲート G1)

### 3.3 シーン読込失敗(`.tscn` ロードエラー)
- ext_resource の `id` 重複・パス誤りを疑う
- 直接編集の不整合をエディタロードで確認
- 巨大シーンなら切り出してロード可能性をテスト

### 3.4 単体テスト失敗
- 期待値と実値の差分を出力
- 直近変更との因果(Git diff の縦横)
- 複数失敗は最も上位の失敗から修正

### 3.5 シナリオテスト失敗 / ハング
- タイムアウト時の **状態スナップショット** を確認
- 入力注入が届いているか(MCP / Input.parse_input_event)
- フレームレート / 物理 / 乱数の決定論性を確認

### 3.6 視覚回帰失敗
- 数値差分が大きい場合、まず Vision で意味的判定
- 意図された変更ならベースライン更新 PR(人間承認)
- ピンク/紫はシェーダ・テクスチャの欠損
- 真っ黒/白は露出 / Sky / Environment の欠損

### 3.7 API 呼出失敗
- 4xx は入力起因(プロンプト / パラメータ / キー)
- 429 はレート、バックオフ後再試行 → 解消なければフェイルオーバー
- 5xx はサーバ起因、N 回後にフェイルオーバー
- ネットワーク断は短時間再試行 → 失敗

### 3.8 シークレット未設定 / 失効
- 該当環境変数の存在 / 値の長さを確認(中身は出力しない)
- 失効疑いはプロバイダ側で確認 → ローテーション
- `02_services/secrets_management.md` の手順

### 3.9 LFS フェッチ失敗
- LFS 認証の確認
- 大容量で帯域不足ならミラー / キャッシュ
- 必要ファイルのみフェッチに切替

### 3.10 CI 失敗
- 失敗ジョブの直近成功と差分(コードか CI 設定か)
- ランナー OS 差(Windows 改行 / パス区切り / 文字コード)
- Flaky の特定(再実行で通るが根本原因不明 → 別途タスク化)

### 3.11 ビルド失敗
- インポート → ビルド → 署名 のどこで落ちたか
- プラットフォーム別(署名・公証・キーストア)
- 差分を `release.yml` の前回成功から比較

### 3.12 配布失敗
- ストア固有のバリデーション失敗(年齢分類、必須メタデータ)
- 署名・公証期限切れ
- アカウント権限・契約状態

### 3.13 マージコンフリクト
- 3-way diff の理解 → 意図に従って解決
- `.tscn` のような順序の意味が薄いテキストは慎重に
- 不明なら **コンフリクト発生側** にレビュー依頼

### 3.14 視覚的に「何かおかしい」(Vision 検出)
- ピンク → マテリアル・シェーダ
- 真っ黒 → ライト・Environment
- 真っ白 → 露出・空気感
- Z-fighting → 同位置面、深度バッファ
- 縞 → 整数化・量子化・mipmap
- ジャギ → MSAA / FXAA / TAA 設定

### 3.15 パフォーマンス劣化
- 直近変更とプロファイル結果を突合
- 頻発ノード(Particles / Light / Shadow / Physics)
- メモリリーク疑いは長時間プレイで再現

### 3.16 Claude Code 自身の混乱(計画と実装の乖離)
- 直前数発言を要約 → 新セッション
- `pipeline/decisions/` に経緯を残してリセット

## 4. リトライ上限

- 同一エラーで連続 N 回失敗(目安 3 回)したら自動修正を停止しエスカレーション
- ループから抜けることを優先(無限改善より人間判断)

## 5. 学習

- 同じ失敗が 2 回以上発生したら **テストを追加**
- 規約に反する原因なら規約を強化
- ドキュメント不足ならドキュメントを更新

## 6. 失敗を隠さない

- 完了報告に「テスト緑」と書くなら **本当に緑のときだけ**
- 部分的な完了は明示
- ユーザに不利益が及ぶ可能性のある事象は即時通知
