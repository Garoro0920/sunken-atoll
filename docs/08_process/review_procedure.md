# レビュー手順

## 1. 目的

コード・シーン・アセット・ドキュメント変更に対する **レビュー(自動 + 人間)** の標準手順を定める。

## 2. レビューの目的

1. **正しさ**: 仕様との一致、論理整合
2. **規約準拠**: `04_standards/` 配下と整合
3. **保守性**: 将来の改修コストを下げる構造
4. **安全性**: 機密漏洩・脆弱性・破壊的副作用がない
5. **学び**: 設計選択の明文化、知見共有

## 3. レビューの種別

| 種別 | 担当 | 範囲 |
|---|---|---|
| 一次レビュー | Claude Code | 全 PR |
| 規約レビュー | リンタ + Claude Code | 全 PR |
| 設計レビュー | 人間(必要時) | 大型変更、API 影響、基盤改修 |
| セキュリティレビュー | 専用エージェント or 人間 | 認証・暗号・入力境界 |
| ビジュアルレビュー | Claude Vision + CD | 主要シーン変更 |
| ライセンスレビュー | 自動 + 必要時人間 | 依存追加 / 削除 |
| 法務レビュー | 専門家 | 契約・規制対象機能 |

## 4. PR 提出側の責務

- ブランチ命名規約遵守(`branching_and_commits.md`)
- PR 説明文に **目的 / 変更範囲 / 検証方法 / 影響 / リスク** を記載
- 関連 spec / Issue / docs へのリンク
- スクリーンショット(UI/3D 変更時)
- 自動チェック緑であることを確認

### 4.1 PR テンプレート(雛形)

```
## 目的
<spec/issue へのリンク + 1 文要約>

## 変更内容
- <要点を箇条書き>

## 検証方法
- 単体: <該当テスト>
- 統合: <該当テスト>
- 視覚: <該当シーン>
- 手動: <あれば手順>

## 影響範囲
- 規約: 影響あり/なし(ある場合は更新リンク)
- API: 影響あり/なし
- 性能: 影響あり/なし
- ライセンス: 影響あり/なし

## スクリーンショット
<UI/3D 変更時>

## リスク
- <考えられる副作用と対処>

## チェックリスト
- [ ] G1 緑
- [ ] テスト追加 / 更新
- [ ] ドキュメント更新
- [ ] CHANGELOG 更新(必要時)
```

## 5. レビュアの責務

- 提出側の意図を正しく理解する(まず説明文と spec を読む)
- 機械的に検出できる事項は CI に任せ、レビュアは**設計と意図**に集中
- 指摘は **具体・建設的・代替提案つき**
- 致命的な指摘とスタイル指摘を区別する(後者は積極的にコメント数を絞る)

## 6. Claude Code の一次レビュー観点

```
[1] 仕様 / Issue との一致
[2] 規約準拠(coding/asset/scene/naming)
[3] テスト追加の妥当性
[4] エッジケース・障害パスの扱い
[5] 性能影響
[6] セキュリティ(入力検証 / 認証 / シークレット)
[7] ドキュメント整合
[8] 不要変更・スコープ逸脱
[9] 公開ドキュメントへのバージョン番号混入(本テンプレ規律)
[10] ライセンス・帰属表示
```

## 7. レビュー指摘の重大度

| Lv | 例 | 対応 |
|---|---|---|
| Blocking | 規約違反、セキュリティ、設計の致命欠陥 | 修正必須、マージ不可 |
| Should | 強く推奨だが致命ではない | 同 PR 内で対応推奨 |
| Nit(細目) | 命名の好み、コメント追加 | 任意、同 PR/別 PR どちらでも |
| Praise | 良い点 | 残す(レビューの空気) |

## 8. 視覚レビュー

- 主要シーン変更があれば自動 Vision レビュー結果を PR にコメント
- 美的判断・ブランド整合は CD に依頼
- 差分を「許容 / 修正 / ベースライン更新」のいずれかで判定

## 9. ライセンスレビュー

- 新規依存追加時に自動チェック
- 互換性違反は Blocking
- ライセンス文書 URL が記録されているか確認

## 10. セキュリティレビュー

- 入力境界(ユーザ入力、ネットワーク、ファイル)を確認
- シークレットの取扱
- 既知 CVE のチェック
- 認証・認可の経路

## 11. レビュー所要時間

- 小: 30 分以内
- 中: 1〜2 時間
- 大: 半日以上(分割推奨)

レビュー時間の長期化は分解不足のサイン → `task_decomposition_policy.md`

## 12. レビュー反復

- 修正コミットは「Review feedback addressed」のような明示
- 大規模な追加変更は新 PR にする(レビュー履歴の維持)
- 解決済コメントは resolve、未解決は理由付きで残す

## 13. 自動マージ条件

以下すべてを満たすときに限り自動マージ可:
- G1 / G2 緑
- レビュアが Approve
- 規約違反 0
- 競合なし

それ以外は手動マージ。

## 14. アンチパターン

- LGTM のみで実質レビューなし
- 数千行 PR をそのままレビュー(差戻して分割)
- 自動チェックが拾うべき内容を人間が指摘し続ける
- 嗜好レビューで Blocking 扱い
- レビューが学びの場でなく闘争の場になる
