# 意思決定ログプロトコル(ADR / RFC)

## 1. 目的

設計判断・採用変更・運用方針の **意思決定** を記録し、なぜその選択をしたかを未来の自分・他人・Claude Code が理解できる状態に保つ。

## 2. 文書種別

| 種別 | 用途 | 配置 |
|---|---|---|
| Decision Log | 軽量な意思決定の記録 | `pipeline/decisions/<date>_<topic>.md` |
| ADR(Architecture Decision Record) | 構造的・アーキテクチャ的な決定 | `docs/adr/<NNNN>-<title>.md`(プロジェクトで採否) |
| RFC(Request for Comments) | 大規模変更の事前提案 | `docs/rfcs/<NNNN>-<title>.md`(プロジェクトで採否) |

軽量プロジェクトでは Decision Log のみで十分。ADR / RFC は規模に応じて導入。

## 3. Decision Log フォーマット

```
# YYYY-MM-DD <短いタイトル>

## 文脈
<背景。なぜ意思決定が必要か。>

## 選択肢
- A: 概要 / 利点 / 欠点
- B: 概要 / 利点 / 欠点
- C: 概要 / 利点 / 欠点

## 決定
<採用した選択肢と理由>

## 結果
<期待される効果。リスクとの引き換え。>

## フォロー
<必要なフォロータスク・期限・指標>

## 関連
<spec / Issue / docs / コミット>
```

短くて構わない。**残すこと自体** が価値。

## 4. ADR フォーマット(オプション)

```
# NNNN. <タイトル>

- 状態: Proposed | Accepted | Deprecated | Superseded by ADR-MMMM
- 起票日: YYYY-MM-DD
- 決定日: YYYY-MM-DD

## 文脈
## 決定
## 結果
## 代替案
## 参考
```

採用後は **不変**。状態変更はメタデータのみ更新、内容は履歴を保つ。

## 5. RFC フォーマット(オプション)

```
# NNNN. <タイトル>

- 著者: <名前 or Claude Code>
- 状態: Draft | In Review | Accepted | Rejected
- 起票日: YYYY-MM-DD

## 要約
## 動機
## 提案
## 代替案
## マイグレーション計画
## 影響(性能 / 互換性 / セキュリティ / 運用)
## 未解決事項
```

レビュー期間を設け、コメントを集約する。

## 6. いつ Decision Log を書くか

- 採用 / 不採用の判断
- 仕様の重要解釈
- 例外運用の許可
- フェイルオーバー実行(API 切替)
- ベースライン大幅更新
- リファクタの方針転換

## 7. いつ ADR を書くか(該当時)

- アーキテクチャ層の追加・削除
- データモデルの大規模変更
- 主要ライブラリ・フレームワークの採用変更
- 性能/可用性 SLO の決定

## 8. いつ RFC を書くか(該当時)

- 影響範囲が広く、複数領域に跨る変更
- 複数の選択肢があり議論が必要
- 外部関係者を含む合意形成

## 9. 文書間の関連付け

- Decision Log は spec / コミット / PR にリンク
- ADR は関連 ADR を相互参照(`Supersedes`, `Superseded by`)
- RFC は採用後に ADR 化 or 規約改訂へ反映

## 10. Claude Code の関与

- 重要決定の **草案** を Claude Code が作成可
- 最終決定は人間が承認
- 過去の Decision Log を参照し、矛盾を指摘する
- 古い記録は削除せず、状態を更新する

## 11. プライバシー / 機密

- 個人名・契約金額などはマスク or 別ファイル
- 公開リポジトリで運用する際は事前にレビュー
- 法務・人事に関わる事項は別管理

## 12. アンチパターン

- 「会議録の長文貼付」(要点だけに)
- 「決まったので記録不要」(後で必ず必要になる)
- ADR の「決定」を後から書き換える
- RFC が議論なしで Accepted になる
