# 障害対応ワークフロー

## 1. 目的

開発中・運用中に発生する障害(クラッシュ、品質ゲート恒常的失敗、API 障害、漏洩、ストア取り下げ等)に対する **段取りと役割分担** を規定する。

## 2. 障害カテゴリ

| カテゴリ | 例 |
|---|---|
| ランタイムクラッシュ | プレイヤー側で発生する例外、CTD |
| 進行不能 | 特定操作で詰むシナリオバグ |
| パフォーマンス劣化 | リリース後の FPS 低下、メモリ膨張 |
| API 障害 | 外部生成系の停止・大幅遅延 |
| シークレット漏洩 | API キー / 署名鍵の流出 |
| 法務インシデント | 著作権クレーム、ライセンス違反指摘 |
| ストア取下げ | プラットフォーマからの違反通知 |
| データ毀損 | セーブデータ/サーバ DB の破損 |

## 3. 検知

- 自動: Sentry、CI 失敗、視覚回帰恒常的失敗、利用者報告メールフォーム
- 手動: ユーザフィードバック、ストアレビュー、コミュニティ報告

## 4. 重大度

| Sev | 定義 | 例 | 初動 SLA(目安) |
|---|---|---|---|
| Sev1 | 全プレイヤー影響、サービス停止 | サーバ全断、CTD 多発、漏洩 | 即時 |
| Sev2 | 多数影響、進行不能 | メインクエスト詰み | 24h |
| Sev3 | 限定影響 | 一部プラットフォームのみのバグ | 数日 |
| Sev4 | 軽微 | UI 表示崩れ、誤字 | 次リリース |

具体時間はプロジェクト開始時に確定。

## 5. 共通フロー

```
[1] 検知 → トリアージ(Sev 判定)
[2] 一次対応者の指名(オペレータ + Claude Code)
[3] 影響評価(範囲・件数・累積)
[4] 一次封じ込め(必要なら機能フラグ無効化、サーバ停止、配信停止)
[5] 根本原因分析
[6] 恒久対応(コード修正、データ修復、契約見直し等)
[7] 検証(テスト、視覚回帰、本番監視)
[8] 復旧(段階的な再リリース)
[9] ポストモーテム(原因・経過・対策・再発防止)
[10] ドキュメント反映(規約/手順/ガード追加)
```

## 6. シークレット漏洩

1. 該当キーを **即時無効化**(各サービス管理画面)
2. 新規キー発行、CI/環境変数更新
3. Git 履歴を確認、必要なら `git filter-repo` で過去ごと除去 + 強制プッシュ
4. 影響範囲に応じて利用者通知(プライバシー含む場合)
5. 漏洩経路を特定(コミット / ログ / スクリーンショット / 対話貼付)
6. 再発防止: pre-commit / CI スキャン強化、対話プロトコル教育

## 7. API 障害

- 該当 API を一時的に **代替プロバイダ** にフェイルオーバー(`02_services/service_catalog.md` 参照)
- 影響範囲が広い場合 dry-run モードで凌ぐ
- 復旧後、品質劣化がないか比較
- 長期障害なら採択変更を検討

## 8. ランタイムクラッシュ

1. Sentry イベントを Claude Code(Sentry MCP)で取得
2. スタックトレース・ブレッドクラム・カスタムタグを解析
3. 再現手順(BugCraft 様の手順生成)→ ローカル/CI で再現
4. 修正 → 単体/統合/シナリオテスト追加 → リリース
5. 既知の同類エラーの抑制ルールを Sentry 側に登録

## 9. 進行不能

1. 該当シナリオの状態 dump を取得(プレイヤー/ワールド/クエスト)
2. 該当シナリオの自動シナリオテストを追加(回帰防止)
3. ホットフィックス、もしくはセーブデータ補正(慎重に)

## 10. パフォーマンス劣化

1. 監視ダッシュボードで指標を確認
2. プロファイラ取得(該当場面で)
3. ボトルネック特定 → 修正(描画 / GC / 物理 / I/O)
4. 視覚品質劣化を伴う場合は CD と協議

## 11. 法務インシデント

1. 当該アセット/コードの利用を **即時停止**(CDN / 配布バイナリ)
2. 法務助言を仰ぐ(弁護士・契約サービスの問合せ窓口)
3. 該当部分を差し替え、再リリース
4. アセットメタデータと `07_governance/licensing.md` を確認・修正

## 12. ストア取り下げ

1. 通知文を確認、違反項目を特定
2. プラットフォーマと連絡(問合せ窓口経由)
3. 修正 → 再申請
4. 影響を受けるユーザへの説明文・代替手段の用意

## 13. ポストモーテム

- 5W1H + 時系列 + 直接原因 + 根本原因 + 是正措置 + 再発防止策
- 公開可能な範囲をユーザ向けに公開する判断は PO が行う
- 内部記録は `pipeline/postmortems/` に保管

## 14. ドリル

- 主要障害カテゴリは年 1 回以上の **机上訓練** を実施
- 想定シナリオに沿って Claude Code が手順を再演
